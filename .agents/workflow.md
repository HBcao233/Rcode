# Agent 工作流程

本文件定义 agent 如何接收任务、执行、验证和交付。

## 1. 角色划分

| 角色 | 职责 | 典型执行者 |
|---|---|---|
| 人类负责人 | 决定目标、里程碑、审批 ADR、合并主分支 | 项目所有者 |
| 规划 agent | 拆解需求为任务单，更新 `roadmap.md` 与 `backlog.md` | 大模型 agent，只写文档不写代码 |
| 实现 agent | 按任务单修改代码和测试 | 大模型 agent |
| 审查 agent | 对照规范和 DoD 审查 diff，给出阻塞/建议意见 | 独立会话，不参与实现 |

同一个会话不应同时担任实现和审查。

## 2. 任务生命周期

```
Backlog ──► Ready ──► In Progress ──► Review ──► Done
   │          │            │             │
   └─ 待确认   └─ 需求完整   └─ 有失败测试   └─ 审查未通过 → 回到 In Progress
```

- **Backlog**：想法或未明确的需求。
- **待确认**：缺少关键信息，需要人类回答。Agent 不得自行假设。
- **Ready**：任务单字段完整（目标、范围、验收标准、涉及模块）。
- **In Progress**：agent 已领取，并在任务单中记录分支名。
- **Review**：代码完成，通过 DoD 自检，等待审查。
- **Done**：已合并，任务单归档。

## 3. 标准执行循环

每个实现 agent 按下面的顺序工作：

1. **读上下文**：`README.md` → 任务单 → 相关 skill → 相关模块 README。
2. **确认范围**：如果任务单缺少验收标准，停止并在任务单“待确认”中提问。
3. **写计划**：在任务单中列出 3–7 步计划，并标注需要修改的文件。
4. **先写测试**：能用测试表达的行为，先写失败测试。
5. **最小实现**：只改必要的文件，不做顺手重构。
6. **运行检查**：依次运行格式化、lint、单元测试、构建。失败则修复后重跑，不得跳过。
7. **自检 DoD**：对照 `conventions.md` 第 7 节逐项确认。
8. **更新文档**：任务单、必要的模块 README、CHANGELOG。
9. **提交审查**：输出变更摘要、测试结果、遗留问题。

## 4. 权限与安全边界

### Agent 可以自主做的
- 读取、创建、修改本仓库内的源代码、测试、文档
- 运行 `cargo`、`./gradlew`、`ktlint`、`git status/diff/log/add/commit`（本地分支）
- 在功能分支上提交

### 需要人类审批的
- 新增依赖（需通过 `conventions.md` 第 6 节检查，并在 PR 中标注）
- 修改 `.agents/` 中的目标、非目标、里程碑范围
- 创建或修改 ADR 的 Accepted 状态
- 修改签名配置、包名、应用权限（`AndroidManifest.xml` 中的 `uses-permission`）
- 合并到 `main`、发布、推送到应用商店
- 删除超过 1 个文件或删除测试

### 禁止
- 提交密钥、令牌、签名文件
- 修改 CI 以跳过测试或降低检查级别
- 使用 `--no-verify` 跳过 git hooks
- 在没有复现测试的情况下“修复”行为
- 无依据地声称“测试通过”。必须贴出实际命令和结果摘要

## 5. 失败处理

- 同一错误连续修复 3 次仍失败：停止，写入任务单的“阻塞”区，附错误日志与已尝试的方案，请求人类介入。
- 发现需求与文档矛盾：以 `goals.md` 为准；矛盾本身记录到 `backlog.md`。
- 发现已有代码违反规范：不在当前任务中顺带修复，新建 `chore` 任务。

## 6. 交接

任务中断或换 agent 接手时，必须更新任务单的“交接记录”区，包含：

- 当前分支与最后提交哈希
- 已完成和未完成的步骤
- 未通过的测试及原因
- 下一步建议

具体格式见 `skills/task-handoff/SKILL.md`。

## 7. 沟通规范

- 汇报结论在前，细节在后。
- 不确定的地方直接说明，并给出你的推荐选项。
- 不要用“应该可以”代替验证结果。
- 修改文件时写清路径。
